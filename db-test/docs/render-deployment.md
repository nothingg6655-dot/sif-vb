# Deploy the API to Render

The Supabase database and current data are already deployed. Render runs the
Node/Fastify API and both scheduled workers in one service; Flutter uses the Render
HTTPS origin in production builds. No external cron or additional server is used.

For the existing service, import the private, ignored file
`db-test/.env.render.schedulers` with **Environment > Add from .env**. It adds only
the seven scheduler settings and preserves the service's current API credentials.
Then set Docker runtime, clear Root Directory, choose Dockerfile Path
`db-test/backend/Dockerfile` and Docker Build Context `.`, and deploy the latest
`main` commit. Choose an always-on paid instance in the same service's settings
before relying on exact unattended run times.

The verified Linux extraction exceeded 512 MB during PDF processing (about
574 MB in the local container). Use the same service's 1 CPU / 2 GB compute plan
(`1c-2g`, previously Standard; currently $25/month) for headroom. Both Free and
Starter provide only 512 MB; Free also sleeps. Confirm current pricing in the
Render dashboard before changing billing.

## Publish the code changes first

The GitHub repository is `https://github.com/nothingg6655-dot/sif-vb`.
Its root is the local `Backennd/` folder, and the API directory within that
repository is `db-test/backend`. Commit/push the current backend configuration,
the public `backend/certs/supabase-ca.crt`, and `render.yaml` before deploying.
Do not commit `.env.render`, other credential files, or database backups.

## Render service settings

Update the existing **sif-vb Web Service**, keeping its URL and repository:

- Branch: `main`
- Runtime: Docker
- Root Directory: empty (repository root)
- Dockerfile Path: `db-test/backend/Dockerfile`
- Docker Build Context: `.`
- Region: Singapore, matching the Supabase region
- Build/Start Command: clear native-runtime overrides; use the Dockerfile
- Health Check Path: `/health`

Leave the pre-deploy command empty. Render supplies `PORT`; the server reads it.
The image bundles Node, Python and Chromium. Factsheet discovery selects Chromium
on Linux, and the image installs its operating-system dependencies. The backend
validates worker imports and browser startup before becoming ready.

Alternatively, create a Render Blueprint from the repository's root `render.yaml`.
It sets the same configuration and prompts for the API and ingestion passwords. Its
`ADMIN_API_KEY` is generated by Render. The blueprint retains the existing service's
approved compute plan instead of changing billing or resetting a paid instance to
Free. Select an always-on paid plan before relying on unattended schedules. Free web
services sleep after 15 minutes without inbound traffic: internal timers cannot
run while the process is stopped. This limitation cannot be fixed in application
code. No keep-alive service or second server is introduced. Changing the plan
requires the account owner's billing approval.

Do not copy the local `PGSSLROOTCERT=data/...` path into Render. The backend uses
its bundled Supabase public CA when no override is supplied. A custom certificate

The API retains its backend role. Internal workers require separate ingestion
credentials, added manually to the existing Render service (Blueprint updates do
not populate new `sync: false` secrets):

```dotenv

SCHEDULER_SCOPE=render
SCHEDULER_PGUSER=sif_ingestion.pduxixfhejkslwafxplw
```

Do not use the administrator role. Do not add `SIF_ENV_FILE`, local certificate
paths, or credentials to the Docker image, Git repository, or Flutter application.
Apply migration `0008_internal_schedulers.sql` once with the existing migration
runner and an administrator connection before enabling the workers. It creates
only the durable job-state table, with RLS, API read access and ingestion write
access. The Docker build context excludes environment files and downloaded data.
No Supabase URL, anon key or service-role API key is required for this PostgreSQL
connection. Database and admin secrets must never be passed to Flutter.

## Internal scheduling and recovery

The Fastify process starts its scheduler after listening. It reads the server UTC
clock and applies the requested Asia/Kolkata calendar times: factsheets daily at
11:01:59 IST and NAV every even hour at :00:00 IST. A database advisory lock prevents
duplicate workers across rolling deploys. Only one heavy worker runs at a time.
NAV uses the existing source-hash checks and conditional updates, then calculates
derived metrics. Factsheets use online official-source discovery, extraction and
database ingestion. Publisher-level failures remain visible separately from task
completion.

Job state and the latest factsheet coverage are stored in `sif_scheduler_jobs`;
Render filesystem resets do not erase the dashboard's last recorded result. On
restart the scheduler coalesces missed slots into one current-source check. Failed
jobs retry after 5 and 10 minutes, with three attempts per slot. Timeouts and
shutdowns terminate child process groups; interrupted slots recover after restart.
NAV workers have a 90-minute deadline and factsheets a 40-minute deadline.

The public `/api/sync/status` endpoint reads these server records and live NAV
audit data. It never queries Windows tasks in internal mode. Heartbeats are saved
every 30 seconds; reports become unavailable after two minutes without a heartbeat.
Factsheet data checks age independently using their actual check timestamp. The
existing APK already renders this response, so a phone rebuild is unnecessary.

After validating both jobs on Render, disable the two old Windows tasks to avoid
duplicate local polling. Do not disable them before the cloud migration succeeds.

## Flutter development and production

Run commands from `sif_research/`. Local development defaults to
`http://127.0.0.1:3000`. Production builds default to
`https://sif-vb.onrender.com`. Debug defaults to development; release defaults to
production. `API_BASE_URL` can override the origin, without `/api` or a path suffix.

```powershell
# Local Chrome development
flutter run -d chrome --dart-define=APP_ENV=development --dart-define=API_BASE_URL=http://127.0.0.1:3000

# Local Chrome preview using the deployed backend
flutter run -d chrome --dart-define=APP_ENV=production --dart-define=API_BASE_URL=https://sif-vb.onrender.com

# Production web files: build/web
flutter build web --release --dart-define=APP_ENV=production --dart-define=API_BASE_URL=https://sif-vb.onrender.com

# Production Android APK
flutter build apk --release --dart-define=APP_ENV=production --dart-define=API_BASE_URL=https://sif-vb.onrender.com
```

For the Android emulator's local backend, use `http://10.0.2.2:3000` with
`APP_ENV=development`. A USB-connected physical phone can use localhost with the
existing `adb reverse tcp:3000 tcp:3000` workflow.

The production default is configured in `ApiConfig.productionBaseUrl`. An
`API_BASE_URL` override is compiled into the Flutter build, so changing the backend
hostname requires rebuilding and redeploying the Flutter app.

## Ongoing data updates

The Node web service serves API requests. It does not start the Python NAV,
factsheet, or benchmark ingestion jobs. Those continue to use the existing cloud
database configuration and require a separately deployed worker/cron service for
updates while the development computer is off. Do not run migrations or ingestion
as the web service's build/start command.

### IST scheduler configuration

Set both `APP_TIMEZONE=Asia/Kolkata` and `TZ=Asia/Kolkata` on the API and on any
separate ingestion worker. The Python scheduler explicitly sets Asia/Kolkata on
the scheduler and every cron trigger, so the server region never controls its
wall-clock schedule. `TIGZIG_SCHEDULE_INTERVAL_HOURS=2` schedules daily checks at
00:00, 02:00, 04:00, 06:00, 08:00, 10:00, 12:00, 14:00, 16:00, 18:00, 20:00,
and 22:00 IST. Unchanged source checksums skip imports; changed snapshots use the
existing transactional, conditional UPSERT path.

An always-running Python worker uses `python -m ingestion.tigzig.worker scheduler`
from `db-test/`. Its configured startup recovery also runs once immediately on
startup; retries run after delays. Those are recovery behavior rather than daily
cron times. Factsheet polling uses elapsed-second intervals, which are independent
of server timezone. Factsheet month selection explicitly uses the IST date.

Render's native Cron Job schedule is always evaluated in UTC, even when `TZ` or
`APP_TIMEZONE` is set. If using separate Render Cron Jobs instead of the Python
scheduler worker, enter the UTC expressions corresponding to the intended IST
times. For the two-hourly IST schedule above, use `30 */2 * * *` UTC.

Native cron jobs must run a one-shot command such as
`python -m ingestion.tigzig.worker sync`, which exits. Do not use the continuous
`scheduler` command as a Render Cron Job. Choose one scheduling mechanism to avoid
duplicate scheduled runs. The current blueprint defines only the API web service;
it does not deploy or start a Python scheduler worker or native cron jobs.
